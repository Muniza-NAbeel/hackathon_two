# Implementation Plan: AI-Powered Chatbot for Task Management (Phase 3)

**Branch**: `001-ai-chatbot-phase3` | **Date**: 2025-12-30 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/003-ai-chatbot-phase3/spec.md`

## Summary

Phase 3 adds an AI-powered chatbot interface that enables users to manage their todo tasks through natural language conversation. The implementation uses the OpenAI Agents SDK for natural language understanding and the Official MCP SDK to expose stateless task management tools. All conversation state is persisted in PostgreSQL, maintaining a fully stateless backend architecture. The chatbot integrates with Phase 2's existing JWT authentication and task database while operating in complete isolation within the `phase_3/` directory structure.

**Technical Approach**: The architecture follows a strict layering model where the AI Agent cannot access the database directly - all task operations must flow through MCP tools. Each chat request loads conversation history from the database, processes the user's message through the AI agent, executes any tool calls, persists both user and assistant messages, and returns the response. This ensures the backend remains completely stateless while providing conversational continuity across sessions.

- Sub-3-second response time for 95% of chat requests

- Absolute statelessness requirement (no in-memory session state)
- Phase 3 must be fully isolated in `phase_3/` directory
- Zero modifications to Phase 2 code
- AI agent must never access database directly
- All data operations must route through MCP tools only

**Scale/Scope**:
- 5 MCP tools (add_task, list_tasks, complete_task, update_task, delete_task)
- 3 database models (Task [shared], Conversation, Message)
- 1 chat API endpoint (POST /api/chat)

**Structure Decision**: Phase 3 uses a **Web Application Structure** with three primary directories: `backend/` (FastAPI + MCP client), `mcp/` (standalone MCP server), and `frontend/` (Next.js + ChatKit). This structure maintains complete isolation from Phase 2 while sharing only the database connection. The `agents/` directory contains agent specifications rather than code, following the Constitution's mandate that AI agents orchestrate logic through specifications. The `skills/` directory houses reusable Agent Skills for common patterns like conversation loading and JWT verification.

**Key Architectural Decisions**:
1. **MCP Server Isolation**: The MCP server runs as a separate process with its own database access layer, ensuring the AI agent cannot bypass tool boundaries.
2. **Stateless Backend**: The FastAPI backend loads full conversation history from PostgreSQL on every request and persists messages immediately after generation.
3. **Shared Database, Isolated Schema**: Phase 3 shares the Neon PostgreSQL database with Phase 2 but adds new tables (Conversation, Message) without modifying the existing Task table.
4. **Frontend Separation**: The Next.js frontend lives in `phase_3/frontend/` rather than extending Phase 2's frontend, maintaining phase isolation.

### Data Model Design

**Output File**: `specs/003-ai-chatbot-phase3/data-model.md`

#### Entities

**1. Task (Shared with Phase 2)**

**Purpose**: Represents a todo item managed by users. Shared schema with Phase 2.

**Fields**:
- `id` (integer, primary key, auto-increment): Unique task identifier
- `user_id` (string, indexed, not null): Owner identifier (from JWT token)
- `title` (string, max 255 chars, not null): Task title
- `description` (text, nullable): Optional detailed description
- `completed` (boolean, default false, not null): Completion status
- `created_at` (timestamp, default current_timestamp, not null): Creation timestamp
- `updated_at` (timestamp, auto-update, not null): Last modification timestamp

**Validation Rules**:
- `title` must be non-empty after trimming whitespace
- `user_id` must be non-empty and match JWT token user_id
- `completed` defaults to `false` on creation

**State Transitions**:
- Created → Pending (completed = false)
- Pending → Completed (completed = true)
- Completed → Pending (completed = false, re-opening allowed)
- Any state → Deleted (soft delete if needed, or hard delete)

**Indexes**:
- Primary key index on `id`
- Index on `user_id` for fast user-scoped queries
- Composite index on `(user_id, completed)` for filtered listing

**Relationships**:
- No direct relationships from Task (isolation from conversation data)

---

**2. Conversation**

**Purpose**: Represents a chat session between a user and the AI chatbot. Maintains conversation context across requests.

**Fields**:
- `id` (integer, primary key, auto-increment): Unique conversation identifier
- `user_id` (string, indexed, not null): Owner identifier (from JWT token)
- `created_at` (timestamp, default current_timestamp, not null): Conversation start timestamp
- `updated_at` (timestamp, auto-update, not null): Last message timestamp

**Validation Rules**:
- `user_id` must be non-empty and match JWT token user_id
- Conversations are never deleted (archival may be added later)

**State Transitions**:
- Created → Active (first message sent)
- Active → Active (ongoing conversation)
- (No terminal state in Phase 3; archival/deletion deferred to future phases)

**Indexes**:
- Primary key index on `id`
- Index on `user_id` for fetching user's conversations
- Index on `updated_at` for sorting by recency

**Relationships**:
- One-to-many with Message (one conversation has many messages)

---

**3. Message**

**Purpose**: Represents a single message in a conversation, sent by either the user or the AI assistant.

**Fields**:
- `id` (integer, primary key, auto-increment): Unique message identifier
- `conversation_id` (integer, foreign key → Conversation.id, indexed, not null): Parent conversation
- `user_id` (string, indexed, not null): Owner identifier (for security validation)
- `role` (enum: "user" | "assistant", not null): Message sender role
- `content` (text, not null): Message text content
- `created_at` (timestamp, default current_timestamp, not null): Message timestamp

**Validation Rules**:
- `conversation_id` must reference an existing Conversation
- `user_id` must match the parent Conversation's user_id (ownership validation)
- `role` must be either "user" or "assistant"
- `content` must be non-empty after trimming whitespace

**State Transitions**:
- Created → Persisted (message saved to database)
- (Messages are immutable once created; no updates or deletions in Phase 3)

**Indexes**:
- Primary key index on `id`
- Index on `conversation_id` for fast message retrieval
- Composite index on `(conversation_id, created_at)` for chronological ordering

**Relationships**:
- Many-to-one with Conversation (many messages belong to one conversation)
- Foreign key constraint: `conversation_id` → Conversation.id (cascade behavior: restrict delete to prevent orphaned messages)

**Key Design Decisions**:
1. **Task Isolation**: Task table has no foreign keys to Conversation or Message, maintaining clean separation between task data and chat data. MCP tools provide the only access to tasks.
2. **Conversation Ownership**: Both Conversation and Message store `user_id` for double-layer security validation.
3. **Message Immutability**: Messages are write-once; no update or delete operations in Phase 3.
4. **Chronological Ordering**: Composite index on `(conversation_id, created_at)` ensures efficient message retrieval in chronological order.

#### 1. Chat API Contract

**File**: `contracts/chat-api.openapi.yaml`

**Endpoint**: `POST /api/chat`

**Purpose**: Accepts user messages, processes them through the AI agent and MCP tools, and returns assistant responses.

**Request Schema**:
```yaml
ChatRequest:
  type: object
  required:
    - message
  properties:
    message:
      type: string
      minLength: 1
      maxLength: 5000
      description: User's chat message
      example: "Add buy groceries to my list"
    conversation_id:
      type: integer
      nullable: true
      description: Existing conversation ID (null for new conversation)
      example: 42
```

**Response Schema**:
```yaml
ChatResponse:
  type: object
  required:
    - conversation_id
    - response
  properties:
    conversation_id:
      type: integer
      description: Conversation ID (newly created or existing)
      example: 42
    response:
      type: string
      description: AI assistant's response
      example: "I've added 'Buy groceries' to your task list. Task ID: 17."
    tool_calls:
      type: array
      nullable: true
      description: Optional array of tool calls made by the AI
      items:
        type: object
        properties:
          tool_name:
            type: string
            example: "add_task"
          parameters:
            type: object
            example: {"title": "Buy groceries"}
          result:
            type: object
            example: {"task_id": 17, "status": "created", "title": "Buy groceries"}
```

**Error Responses**:
```yaml
ErrorResponse:
  type: object
  required:
    - error
    - message
  properties:
    error:
      type: string
      description: Error code
      example: "UNAUTHORIZED"
    message:
      type: string
      description: Human-readable error message
      example: "Invalid or expired JWT token"
    details:
      type: object
      nullable: true
      description: Additional error context (omitted in production)
```

**Status Codes**:
- `200 OK`: Successful chat processing
- `400 Bad Request`: Invalid request body (missing message, message too long)
- `401 Unauthorized`: Missing, invalid, or expired JWT token
- `500 Internal Server Error`: Unhandled server error (OpenAI API failure, database error)

**Authentication**: Requires `Authorization: Bearer <JWT_TOKEN>` header. JWT token must be valid and issued by Phase 2's Better Auth system.

#### 3. Database Schema

**File**: `contracts/database-schema.sql`

**Purpose**: SQL DDL for creating Phase 3 tables in the shared Neon PostgreSQL database.

```sql
-- Phase 3: AI Chatbot Tables
-- Note: Task table already exists from Phase 2; not recreated here

-- Conversation table
CREATE TABLE IF NOT EXISTS conversations (
    id SERIAL PRIMARY KEY,
    user_id VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_conversations_user_id ON conversations(user_id);
CREATE INDEX idx_conversations_updated_at ON conversations(updated_at DESC);

-- Messages table
CREATE TABLE IF NOT EXISTS messages (
    id SERIAL PRIMARY KEY,
    conversation_id INTEGER NOT NULL,
    user_id VARCHAR(255) NOT NULL,
    role VARCHAR(20) NOT NULL CHECK (role IN ('user', 'assistant')),
    content TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE RESTRICT
);

CREATE INDEX idx_messages_conversation_id ON messages(conversation_id);
CREATE INDEX idx_messages_conversation_created ON messages(conversation_id, created_at);
CREATE INDEX idx_messages_user_id ON messages(user_id);

-- Updated_at trigger for conversations
CREATE OR REPLACE FUNCTION update_conversation_timestamp()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE conversations SET updated_at = CURRENT_TIMESTAMP WHERE id = NEW.conversation_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_conversation_timestamp
AFTER INSERT ON messages
FOR EACH ROW
EXECUTE FUNCTION update_conversation_timestamp();
```

- Use Alembic for schema migrations
- Migration file naming: `{timestamp}_add_phase3_chat_tables.py`
- Ensure Phase 2 Task table is not modified
- Add rollback script for clean development iterations
