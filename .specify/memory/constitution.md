| Attribute | Value |

## II. Project Purpose & Vision

### Evolution Path

This project demonstrates the progressive evolution of a Todo application through five phases:

```
Phase I     Phase II      Phase III       Phase IV          Phase V
   │            │             │               │                 │
   ▼            ▼             ▼               ▼                 ▼
  CLI    →   Web App   →  AI Chatbot  →  Kubernetes   →  Event-Driven
(Python)   (Full-Stack)   (MCP Tools)   (Container)      (Cloud System)
```

### Core Emphases

1. **Spec-Driven Development**: Every feature, agent, tool, and infrastructure component MUST have a specification before implementation.
2. **Reusable Intelligence**: Agent Skills encapsulate domain logic for reuse across phases and features.
3. **AI-Native Architecture**: AI Agents orchestrate business logic; MCP tools execute atomic actions; humans architect, not code.

### Project Nature

This project serves dual purposes:
- **Learning Exercise**: Demonstrates modern cloud-native AI development patterns
- **Production-Grade Architecture**: All artifacts MUST meet production quality standards

## V. Architecture Principles

### Principle 1: Stateless Services

All backend services MUST be stateless. No in-process state beyond request scope.

**Rationale**: Enables horizontal scaling, container orchestration, and fault tolerance.

### Principle 2: Externalized State

All persistent state MUST be stored in:
- Databases (PostgreSQL via Neon)
- Dapr state stores
- External caches

**Rationale**: Decouples compute from storage; enables independent scaling.

### Principle 3: AI Agent Orchestration

AI Agents MUST orchestrate all business logic. Agents:
- Receive user intent
- Decompose into tool calls
- Coordinate multi-step workflows
- Return structured responses

**Rationale**: Centralizes intelligence; enables reasoning and adaptation.

### Principle 4: MCP Tool Atomicity

MCP tools MUST perform single, atomic actions:
- One tool = one action
- No orchestration logic in tools
- Tools are pure functions with side effects

**Rationale**: Composability; agents can combine tools flexibly.

### Principle 5: Agent Skills as Reusable Intelligence

Agent Skills encapsulate reusable patterns:
- Skills are shareable across agents
- Skills encode domain expertise
- Skills reduce duplication

**Rationale**: DRY for AI; accumulated intelligence.

### Principle 6: Event-Driven Communication

Services communicate via events:
- Kafka (Redpanda preferred) for streaming
- Dapr pub/sub for cloud-native messaging
- Async by default; sync only when required

**Rationale**: Loose coupling; temporal decoupling; scalability.

### Principle 7: Loose Coupling, High Cohesion

- Services own their domain completely
- Minimal cross-service dependencies
- Clear bounded contexts

**Rationale**: Independent deployability; team autonomy; maintainability.

## VIII. Governance

### Amendment Procedure

1. Propose amendment via PR to this Constitution
2. Document rationale and impact analysis
3. Require explicit approval from project lead
4. Update `CONSTITUTION_VERSION` per semantic versioning
5. Update `LAST_AMENDED_DATE`
6. Propagate changes to affected templates

### Versioning Policy

- **MAJOR** (X.0.0): Backward-incompatible principle changes, rule removals
- **MINOR** (x.Y.0): New principles, sections, or material expansions
- **PATCH** (x.y.Z): Clarifications, typo fixes, non-semantic changes

### Compliance Review

All artifacts MUST be validated against this Constitution:
- Pre-merge: Automated checks where possible
- PR review: Manual Constitution compliance check
- Post-deploy: Periodic audit against principles

### Conflict Resolution

In case of conflict between documents:
1. This Constitution takes precedence over all other documents
2. Specs take precedence over implementation
3. Explicit rules take precedence over implicit conventions
